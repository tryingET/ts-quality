# AI-agent migration instructions — ts-quality v0.4.0

## Start here

The breaking change itself is documented in `CHANGELOG.md` under `0.4.0` → `### Breaking Changes`. Treat the changelog as the authoritative release-history surface.

Use this file as the AI-agent playbook for resolving that breaking change in downstream consumers that are upgrading from `ts-quality <0.4.0` to `ts-quality >=0.4.0`.

## Objective

Update consumers so they stop depending on removed top-level `nextEvidenceAction` compatibility fields and instead use the canonical evidence-closure contract:

- `nextEvidenceAction.primaryAction` for what to do next
- `nextEvidenceAction.evidenceBasis` for why that action is next

Affected consumers may include:

- JSON parsers for `run.json`, `report --json`, or `explain` projections
- LLM prompts or harness setup packets that summarize `nextEvidenceAction`
- dashboards or reports that display remaining blockers / next actions
- fixtures, golden outputs, and contract tests
- operator handoff scripts that look for artifact paths or mutation/coverage/witness statuses

## Resolution workflow for AI agents

1. Locate all consumer reads of `nextEvidenceAction`.

   Suggested searches:

   ```bash
   rg "nextEvidenceAction|remainingBlocker|bestNextAction|coverageStatus|witnessStatus|mutationStatus|governanceStatus|artifactPaths"
   ```

2. Classify each hit.

   - If it reads the changelog or release note text, leave it unless the prose is wrong.
   - If it is evergreen first-contact documentation, describe only the current `primaryAction` / `evidenceBasis` contract; do not paste this migration map there.
   - If it is parser, prompt, dashboard, fixture, or test code, migrate it.

3. Replace removed-field reads with current contract reads.

   | Old consumer intent | Use in `0.4.0+` |
   | --- | --- |
   | Explain the remaining blocker | `nextEvidenceAction.primaryAction.rationale` plus the relevant `nextEvidenceAction.evidenceBasis.*` facts |
   | Display the best next action | `nextEvidenceAction.primaryAction.title`, `kind`, `steps`, `commands`, and `completionCriteria` |
   | Inspect coverage status | `nextEvidenceAction.evidenceBasis.coverage` |
   | Inspect witness status | `nextEvidenceAction.evidenceBasis.witness` |
   | Inspect mutation status | `nextEvidenceAction.evidenceBasis.mutation` |
   | Inspect governance status | `nextEvidenceAction.evidenceBasis.governance` |
   | Find handoff artifacts | `nextEvidenceAction.primaryAction.artifactPaths` and the generated run sidecars |

4. Prefer sidecars for LLM/operator handoff flows.

   When present, use:

   - `.ts-quality/runs/<run-id>/next-evidence-action.prompt.md`
   - `.ts-quality/runs/<run-id>/next-evidence-action.ak-task.json`

   Do not infer survivor-remediation instructions by scraping prose if `primaryAction.groups`, `primaryAction.steps`, `primaryAction.suggestedEditFiles`, or the sidecars are available.

5. Update tests and fixtures to fail closed on the old fields.

   Contract tests should reject these removed top-level fields on `nextEvidenceAction`:

   - `remainingBlocker`
   - `bestNextAction`
   - `coverageStatus`
   - `witnessStatus`
   - `mutationStatus`
   - `governanceStatus`
   - top-level `artifactPaths`

## Validation checklist

After migration, run the smallest available consumer test plus one current package smoke. For a target repo, a typical smoke is:

```bash
npx -p ts-quality@0.4.0 ts-quality check --changed <repo-relative-source-file>
npx -p ts-quality@0.4.0 ts-quality report --run-id <run-id> --json
```

Confirm that the migrated consumer:

- reads `nextEvidenceAction.primaryAction`
- reads `nextEvidenceAction.evidenceBasis`
- does not require any removed top-level `nextEvidenceAction` field
- uses `next-evidence-action.prompt.md` or `next-evidence-action.ak-task.json` for LLM/operator handoffs when available
- preserves version-specific migration guidance here or in release/changelog surfaces, not in evergreen first-contact docs
